# Plan: Fix Quick-Match (Auto-Match) panel — show remote players & fallback to offline mode-selection on timeout

## 1. What is actually broken (root-cause)

After auditing the relevant scripts the failure has **two independent causes**. Both must be fixed for the symptoms the user describes.

### 1A. Remote player never appears in slot_1 / slot_2 / slot_3
- `MatchmakingStarter.cs` only writes the **local** profile into `myProfileUI` (one slot). It never reads the lobby roster.
- `QuickMatchService.FindMatch()` is a stub — `Debug.Log("QuickMatchService FindMatch called");` and nothing else (`QuickMatchService.cs:39`). No lobby is created, no lobby is searched, no relay allocation is made. So even if the UI listened to lobby events, there is no lobby to listen to.
- `MatchmakingUIController.playerSlots[]` is declared and exposed in the Inspector but is **never written to** anywhere — only `MatchmakingUIController.statusText` / `timerText` are updated.
- `QuickMatchService` declares the events `OnPlayerJoined(name, avatarIndex, seatIndex)` / `OnPlayerLeft(seat)` / `OnMatchFound` but none of them is ever invoked.
- `LobbyManager.UpdatePlayerSlotsUI()` is the *only* code in the repo that renders the lobby roster — but it operates on `LobbyManager.playerSlots[]` (the **Friends-Lobby** panel), not on `MatchmakingUIController.playerSlots[]` (the **Quick-Match** panel). They are two different UIs that share no rendering code.

### 1B. Timer expiry does not redirect to Mode-Selection panel
- Two independent timers race:
  1. `MatchmakingUIController.SearchTimer` (a Unity coroutine that counts `timer` from 20 → 0).
  2. `QuickMatchService.Update()` that counts `searchTimer` up to `searchTimeout`.
- Only (2) fires `OnTimeout` → `HandleNoPlayersFound`. (1) is dead code that just updates the text.
- `HandleNoPlayersFound` does try to open `ModeSelectionPanel`, but:
  - `PlayOnline()` reloads the scene to **GameScene**; `LobbyManager`/`MenuController` (and their `modeSelectionPanel`) live in the **MenuScene**. `FindAnyObjectByType` returns null and the fallback path silently no-ops.
  - `GameModeManager.isOnlineMode = false` is set **after** the panel is shown, so a stale `isOnlineMode=true` flag survives across the scene reload that `PlayOffline`/`ContinueGame` may trigger.
- The mode-selection UI used post-timeout is the same one used for offline (it asks for 2 / 3 / 4 players + coin slider). That is what the user wants — but the redirect path is broken, not the panel.

## 2. Non-goals (must NOT regress)
- Offline gameplay (`MenuController.PlayOffline` → `ModeSelectionPanel` → `ContinueGame`) — untouched.
- Play-with-Friends lobby (`LobbyManager.CreateLobby` / `JoinLobby` / `UpdatePlayerSlotsUI` / `StartGame`) — untouched.
- Online gameplay (`NetworkGameManager`, `NetworkPlayer`, `NetworkDeckManager`, scene netcode) — untouched.

The fix is **strictly additive** inside the Quick-Match flow:
`MatchMakingStarter → QuickMatchService → MatchmakingUIController`.

## 3. Architecture (keeps MVC boundaries clean)

| Layer | Class | Responsibility |
|------|-------|----------------|
| **Controller (service)** | `QuickMatchService` | Owns the Unity Lobby + Relay lifecycle for **auto-match only**. Fires pure-data events. Knows nothing about UI. |
| **View** | `MatchmakingUIController` | Renders `playerSlots[]`, `statusText`, `timerText`. Subscribes to events from the service. |
| **View-Bootstrap** | `MatchmakingStarter` | One-shot entry point: reads `ProfileData`, fills local slot, asks service to start. |
| **Model (shared, read-only)** | `ProfileData`, `AvatarDatabase`, `GameModeManager` | Already exist; no changes. |

Friend-Lobby keeps its own `LobbyManager.UpdatePlayerSlotsUI` path — the two flows never share mutable state.

## 4. Implementation steps

### Step 1 — Make `QuickMatchService` actually do Quick-Match
File: `Assets/Scripts/QuickMatchService.cs`

Replace the stub `FindMatch()` with the standard Unity Lobby **search-or-create** pattern:

1. Build a `QueryLobbiesOptions` filtered by:
   - `AvailableSlots > 0`
   - `IsLocked = false`
   - custom data `gameMode = "quickmatch"` (so we never accidentally join a Friends-lobby)
   - max results = 8
2. `LobbyService.Instance.QueryLobbiesAsync(opts)`:
   - **If** a lobby is returned → `JoinLobbyByIdAsync(lobbies[0].Id)`, then call existing `UpdatePlayerAsync` to push our `name`+`avatar` (same shape used by `LobbyManager.JoinLobby`).
   - **Else** → `CreateLobbyAsync("QuickMatch", requiredPlayers, opts)` with the same `gameMode="quickmatch"` data, push our profile, then create Relay allocation, store `relayCode` in lobby data, `NetworkManager.StartHost()`. Mirror the working code in `LobbyManager.CreateLobby`/`CreateRelay` — do **not** duplicate it; extract a small `LobbyRelayUtility` static helper if helpful, but only used by Quick-Match path.
3. After join/create: subscribe to `LobbyService.Instance.GetLobbyAsync` polling (use `Unity.Netcode`'s `NetworkManager.OnClientConnectedCallback` to *trigger* a refresh, identical to `LobbyManager.OnClientConnectedRefresh` — copy the pattern, do not couple to it).
4. On every refresh:
   - Rebuild the local roster → invoke `OnPlayerJoined(name, avatarIndex, seatIndex)` for each new player that wasn't seen last tick, `OnPlayerLeft(seat)` for each drop-out.
   - Call `CheckMatchReady()` (already exists).
5. Implement the two `async Task` stubs `StartHostFlow`/`StartClientFlow` with the real Relay allocation/join code (same pattern as `LobbyManager.CreateRelay`/`JoinRelay`).
6. Remove the duplicate timer in `QuickMatchService.Update` — let `MatchmakingUIController` own the single countdown (Step 3). The service still exposes `OnTimeout` so the UI can fire it.

Configurability (no hard-coding):
- `requiredPlayers` (already `[SerializeField]` = 4) — drive every comparison.
- `searchTimeout` (already `[SerializeField]` = 20) — drive the UI countdown via `QuickMatchService.SearchTimeout` public getter.
- `quickMatchTag` (new `[SerializeField] string = "quickmatch"`) — lobby filter value.

### Step 2 — `MatchmakingUIController` subscribes to roster events
File: `Assets/Scripts/MatchmakingUIController.cs`

1. In `OnEnable`, also subscribe to:
   - `QuickMatchService.Instance.OnPlayerJoined += HandlePlayerJoined;`
   - `QuickMatchService.Instance.OnPlayerLeft  += HandlePlayerLeft;`
   - `QuickMatchService.Instance.OnMatchFound += HandleMatchFound;`
2. `HandlePlayerJoined(name, avatarIdx, seat)`:
   - Resolve avatar via `QuickMatchService.Instance.avatarDatabase` (already exposed via a property we add).
   - `playerSlots[seat].SetProfile(name, avatarSprite);`
3. `HandlePlayerLeft(seat)`:
   - `playerSlots[seat].SetProfile("Waiting…", null);`
4. Add `QuickMatchService.Instance.GetSearchTimeout()` and use that for `timer` initial value (eliminates the duplicate `20f` literal).
5. The local slot_0 is filled by `MatchmakingStarter` BEFORE `FindMatch()` is called — this ordering is preserved, so the local player's name/avatar is already on screen by the time `OnPlayerJoined` fires for the host.

### Step 3 — Timer-Timeout → Mode-Selection fallback
File: `Assets/Scripts/MatchmakingUIController.cs`

The fundamental issue: mode-selection UI lives in the **MenuScene**, but Quick-Match runs in **GameScene**. Fix by **returning to the menu scene** when no opponent is found, in the same way `LobbyManager.QuitFromGame` does:

1. `HandleTimeout()` (rewrite):
   ```
   searching = false;
   statusText.text = "No players found. Returning to menu…";
   StartCoroutine(ReturnToMenuForOfflineFlow());
   ```
2. `ReturnToMenuForOfflineFlow()`:
   - Reset state **before** scene load: `GameModeManager.isOnlineMode = false;`
   - `QuickMatchService.Instance.CancelSearch();` (new public method: leaves lobby, shuts down relay if host, clears `currentLobby`).
   - `yield return new WaitForSeconds(2f);` (UX breathing room; configurable via `[SerializeField]`).
   - `SceneManager.LoadScene("MenuScene");`
3. In `MenuController.Start()` (file `MenuController.cs`), add a one-shot branch:
   ```
   if (QuickMatchRedirectPending) {             // static flag set by (2)
       QuickMatchRedirectPending = false;
       MenuUI.SetActive(false);
       ModeSelectionPanel.SetActive(true);
       ModeSelectionPanel.GetComponent<ModeSelectionController>().SetHeader("Offline");
   }
   ```
   This guarantees the user lands on the *same* Mode-Selection screen used by offline, with no extra click.

The previous in-place swap of panels in `HandleNoPlayersFound` is removed — it never worked cross-scene anyway and was the source of the "timer expires but nothing happens" bug.

### Step 4 — `MatchmakingStarter` ordering
File: `Assets/Scripts/MatchMakingStarter.cs`

Already correct: fills local slot → calls `FindMatch`. Only change: guard `if (QuickMatchService.Instance == null) { … }` should fall back gracefully (log error and `HandleTimeout` immediately so the user is not stuck).

### Step 5 — Wiring in the Unity Editor (no code, but must be done)
- In the GameScene, on the MatchmakingUIController GameObject: ensure the new `playerSlots[]` array size matches `requiredPlayers` (4) and that slot 0 is the local-player slot that `MatchmakingStarter.myProfileUI` points at. The two fields should reference the same `PlayerProfileUI` instance.
- On `QuickMatchService`: assign the `AvatarDatabase` reference (currently null/unassigned — grep showed the `[SerializeField] AvatarDatabase avatarDatabase` exists but is not used).
