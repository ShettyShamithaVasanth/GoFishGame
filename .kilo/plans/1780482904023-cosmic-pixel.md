# Fix: Online Go Fish — Drawn Card Appears Doubled for ~1 Second

## Bug Description

In online "Play with Friends" mode, when Player A asks Player B for a rank and gets "Go Fish", Player A draws from the deck. The drawn card **appears twice (doubled)** in Player A's hand for about 1 second, then becomes correct (single). Offline mode works correctly.

## Root Cause

There are **two overlapping state syncs** that race with the client-side animation coroutine:

### Timeline (server-side)

```
T=0s   : RequestCardRpc → Go Fish (target doesn't have card)
         → Send TurnResultClientRpc (Phase 1: "Go Fish!")
         → StartCoroutine(DelayedStateSync(5f))  ← SYNC A (fires at T=5s)

T=~4s  : Player clicks deck → RequestDrawFromDeckRpc
         → Server draws card, adds to NetworkPlayer.hand
         → Send TurnResultClientRpc (Phase 2: drawn card value)
         → StartCoroutine(DelayedStateSync(2.5f))  ← SYNC B (fires at T=~6.5s)

T=5s   : SYNC A fires → BroadcastStateToAll()
         → Server's hand NOW INCLUDES the drawn card (added at T=4s)
         → Sends hand to client via ApplyPrivateHand

T=6.5s : SYNC B fires → BroadcastStateToAll() (correct, no issue)
```

### Client-side race condition

```
T=~4.1s : Client receives Phase 2, starts PlayTurnResultCoroutine
          → turnActionRunning = true
          → AnimateCardMove starts (~0.85s animation)

T=~5.1s : SYNC A arrives DURING animation yield
          → ApplyPrivateHand: Clear() → re-add from server (includes drawn card)
          → turnActionRunning=true → NO UI refresh (guard at line 1820)
          → Local hand data now has the drawn card (from server sync)

T=~4.95s: Animation ends (may be before or after sync depending on timing)
          → players[askerId].AddCard(drawn)  ← ADDS DRAWN CARD AGAIN
          → RefreshAllHands()  ← SHOWS CARD TWICE (once from sync, once from AddCard)

T=~6.6s : SYNC B arrives → ApplyPrivateHand: Clear + re-add → correct (1 card)
          → Doubling resolved after ~1-1.5 seconds ← matches user's report
```

**The overlap window:** If the player clicks the deck ~4-5 seconds after the Go Fish result, SYNC A (from Phase 1) arrives during the Phase 2 animation. `ApplyPrivateHand` adds the drawn card from the server. When the animation ends, `AddCard(drawn)` adds the same card again. Result: doubled card for ~1 second until SYNC B corrects it.

### Why this doesn't affect offline mode

Offline mode uses `DrawCardWithAnimation()` which has no network sync. The card is added once and the UI refreshes once.

## Fix — Remove the redundant state sync from the Go Fish case

### Change: `NetworkGameManager.cs` line 568

The Go Fish case in `RequestCardRpc` starts a `DelayedStateSync(5f)` that is **unnecessary** because:
- No cards were transferred (Go Fish = no match)
- No books were formed (the card hasn't been drawn yet)
- The hand state hasn't changed from what was last synced
- `RequestDrawFromDeckRpc` already starts its own `DelayedStateSync(2.5f)` for proper post-draw sync

**Current code** (`NetworkGameManager.cs` lines 564-570):
```csharp
            result.InitializeArrays();

            TurnResultClientRpc(result);

            StartCoroutine(DelayedStateSync(5f));

            return;
```

**Fixed code**:
```csharp
            result.InitializeArrays();

            TurnResultClientRpc(result);

            return;
```

**Remove line 568:** `StartCoroutine(DelayedStateSync(5f));`

This eliminates SYNC A entirely. The only state sync that runs is SYNC B from `RequestDrawFromDeckRpc` (line 703), which fires 2.5s after the draw — well after the animation completes (~0.85s), so there's no race condition.

### Why SYNC B is safe (no race)

- SYNC B fires at T=2.5s after server processes draw
- Client's Phase 2 animation takes ~0.85s
- Client's `AddCard(drawn)` runs at ~0.85s + latency
- SYNC B arrives at ~2.5s + latency
- Since 2.5s > 0.85s, SYNC B ALWAYS arrives after `AddCard`
- `ApplyPrivateHand` clears and re-adds from server → correct, no doubling

### Verification: SUCCESS case is unaffected

The SUCCESS case (`RequestCardRpc` line 575-577) keeps its `DelayedStateSync(5f)` because cards WERE transferred and books may have formed — the sync is needed there. For SUCCESS, all `AddCard` calls complete within ~3s (animation time for transferred cards), and the sync fires at 5s, so there's no overlap.

## Why This Is Safe

1. **Offline mode unaffected** — change is in `NetworkGameManager.cs` which only runs in online mode
2. **No architecture changes** — removing an unnecessary sync, not adding new behavior
3. **Phase 2 sync still handles everything** — `RequestDrawFromDeckRpc` line 703 already syncs state after the draw
4. **Lobby/gameplay flow unchanged** — only affects the Go Fish card draw timing
5. **No hardcoded values** — just removing a redundant coroutine start
6. **SUCCESS case preserved** — the `DelayedStateSync(5f)` on line 577 for the SUCCESS case remains unchanged
